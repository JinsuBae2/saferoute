# saferoute 개발계획서

[기획서](01-project-proposal.md)의 F01~F10을 누가, 어떤 순서로 개발하고 확인할지 정하는 문서다. 개발 목적은 **상황에 따라 방향을 바꾸는 유도등 제어 시스템**이며 시뮬레이션은 검증 환경이다.

설치 명령·OS별 준비·서버 운영 매뉴얼은 이 문서에서 다루지 않는다. 개발 전 합의할 범위·역할·협업 방식·개발 순서·완료 기준을 정리한다. 상세 데이터와 API는 [05번 명세서](05-data-interface-spec.md)를 따른다.

## 1. 개발 범위

화요일에는 다음 흐름이 실제 프로그램으로 연결되어야 한다.

```text
실제 영상 AI / 가상 감지기
→ 관측 상태 통합
→ 위험 구간을 제외한 경로 계산
→ 유도등별 명령
→ 별도 단말 표시·적용 응답
```

- 3D 관제를 닫아도 입력·제어·별도 단말·기록이 유지된다.
- 연기 변화는 구역별 시나리오로 표현한다. 제어기는 시험 정답 대신 전달받은 관측만 사용한다.
- 실제 AI, 가상 설비, 수동 시험의 출처를 구분한다.
- 건물은 공개 안내도 기반 1~3층이며, 설비 배치·치수·통행 조건은 시연 가정으로 기록한다.
- 실제 구조에 없는 우회 통로를 만들지 않는다. 경로가 없으면 이유와 함께 안내 불가로 표시한다.
- 장애물 감지·고급 연기 효과·신규 모델 학습은 핵심 연결의 선행 조건으로 두지 않는다.

실제 설비 연결·제품 인증·물리적 연기 확산·피난 시간 개선은 이번 소프트웨어 시험의 입증 범위 밖이다.

## 2. 기술 구성

| 영역 | 기준 | 이유·책임 |
| --- | --- | --- |
| AI·제어 | Python 3.12, FastAPI, Pydantic | 실제 추론 이벤트와 제어 연결, 입력 검증 |
| 웹 | React, TypeScript, Vite | 관제와 별도 유도등 단말 |
| 3D | Three.js, 좌표 JSON, 필요 시 GLB | 기본 구조·연기·경로 표시 |
| 저장 | JSON 설정, JSONL 실행 로그 | 초기 DB 서버 없이 재현 가능한 기록 |
| 통신 | HTTP 이벤트 전송, 주기 조회·ACK | 작은 규모에서 연결·장애 확인이 단순 |
| 검증 | pytest, 프론트 타입 검사·Vitest, 실제 통합 시험 | 판단·전송·표시를 구분해 확인 |
| 배포 | 지원 Ubuntu 서버, Nginx·systemd, S3 | 공동 실행·프로세스 유지·자료 보관 |

Python 3.12·Node 24.x를 기준으로 하며 패키지는 잠금 파일로 공유한다. AI 환경은 제어 환경과 분리한다. 가중치·추론 라이브러리는 실제 모델 확인 후 고정한다. 최신 버전이라는 이유만으로 제출 직전에 변경하지 않는다.

현재 상태는 메모리에서 관리하고 백엔드는 한 worker로 실행한다. 별도 DB·메시지 브로커는 초기 범위에 넣지 않는다. 모델 성능·GPU·추론 속도는 확인 전 가정하지 않는다.

## 4. 팀 협업 규칙

### 4.1 공통 작업 흐름

```text
이슈 선택·담당 지정
→ 최신 develop에서 규칙에 맞는 브랜치 생성
→ 코드·문서 작성과 로컬 확인
→ 규칙에 맞는 커밋
→ 작업 브랜치 push
→ 템플릿을 작성해 develop 대상 PR
→ CI 통과·충돌 없음 확인
→ 작성자가 Squash merge
→ 작업 브랜치 삭제·develop 갱신
```

**리뷰 승인은 필수가 아니다.** 코드 오너 승인·최근 push의 타인 승인도 요구하지 않는다. 작성자가 확인 항목을 책임지고 CI 통과 후 직접 머지한다. 공통 계약 변경 시 상대 담당과 내용은 공유하되 별도 승인 절차로 머지를 묶지 않는다.

### 4.2 이슈 선택과 작성

- 한 이슈는 한 사람이 끝내고 확인할 수 있는 작업 단위로 만든다.
- 착수 전 자신을 Assignee로 지정한다. 이미 담당자가 있는 이슈는 중복 착수하지 않는다.
- 개발계획서의 A01·B02 같은 작업 ID와 요구사항 F번호를 연결한다.
- 너무 큰 작업은 여러 이슈로 나누고 선행 이슈 번호를 적는다.
- 기본은 **이슈 1개 → 브랜치 1개 → PR 1개**다.
- 이슈 제목은 `<type>(<scope>): <작업 내용>`으로 쓴다. 예: `feat(ai): [A02] 실제 추론 이벤트 연결`. 이슈 번호는 GitHub가 자동 부여한다.
- 완료 조건은 “구현” 대신 확인할 동작으로 적는다. 예: “A 구역 차단 시 S→B→Y 반환”.

실제 템플릿: [작업 이슈 템플릿](../.github/ISSUE_TEMPLATE/task.md)

```markdown
## 목적
무엇을 해결하는가?

## 관련 항목
- 개발 작업: B02
- 요구사항: F04
- 선행 이슈: 없음 또는 #번호

## 작업 범위
- 이번 이슈에서 변경할 내용

## 완료 조건
- [ ] 확인 가능한 결과

## 검증 방법
입력, 기대 결과, 실행할 검사

## 참고·인계
관련 문서, 받는 담당, 주의 사항
```

상태는 Assignee와 이슈·PR로 관리한다. 미할당은 대기, 담당 지정은 진행, PR 생성은 통합 대기, 머지 후 이슈 종료는 완료다. 별도 복잡한 보드 운영을 필수로 두지 않는다.

### 4.3 브랜치 컨벤션

| 종류 | 이름 |
| --- | --- |
| 기본·팀 통합 브랜치 | `develop` |
| 검증·시연·배포 브랜치 | `main` |
| 작업 브랜치 | `<type>/<issue-number>-<kebab-case-description>` |
| 예시 | `feat/12-fire-events`, `fix/18-expired-command`, `docs/23-api-spec` |

- type은 `feat / fix / docs / refactor / test / chore` 중 하나다.
- 번호는 실제 선택한 이슈 번호다.
- 설명은 영어 소문자·숫자·하이픈을 사용한다. 공백·한글·언더스코어는 쓰지 않는다.
- 장기 브랜치는 develop·main만 사용한다. 이슈별 브랜치는 짧게 유지한다.
- develop·main 직접 push·강제 push·삭제는 금지한다.
- 저장소의 첫 기준 커밋만 초기화 예외로 두고, 이후 변경은 PR을 거친다.

```sh
git switch develop
git pull --ff-only origin develop
git switch -c feat/12-fire-events
```

예제의 12와 작업명은 실제 이슈에 맞게 바꾼다.

### 4.4 커밋 컨벤션

**양식:** `<type>(<scope>): <변경 내용> (#<issue-number>)`

| type | 사용 |
| --- | --- |
| feat | 새 기능 |
| fix | 오류 수정 |
| docs | 문서 수정 |
| refactor | 동작을 유지하는 구조 정리 |
| test | 시험·검증 코드 |
| chore | CI·설정·의존성·저장소 관리 |

```text
feat(ai): 영상 감지 이벤트 생성 (#12)
fix(frontend): 만료된 명령의 화살표 제거 (#18)
docs(api): 관측 이벤트 계약 정리 (#23)
chore(infra): 백엔드 CI 검사 추가 (#27)
```

- scope는 변경 영역이다. `ai / backend / frontend / model / data / test / infra / docs`를 기본으로 하며 `routing / guidance / api` 같은 기능 이름도 허용한다. 영어 소문자·숫자·하이픈을 사용하고 사람 이름은 넣지 않는다.
- scope는 생략하지 않는다. 설명은 한글 또는 영어로 쓰되 실제 변경을 설명한다. `수정`·`작업 중`·`최종`만 쓰지 않는다.
- 커밋 번호는 해당 작업 브랜치의 이슈와 일치시킨다.
- 서로 관련 없는 작업을 한 커밋·PR에 묶지 않는다.
- 임시 실패 상태를 공유해야 하면 Draft PR로 올린다. 실패 CI를 무시하고 머지하지 않는다.
- `[skip ci]`·`[ci skip]` 등 CI 생략 문구는 사용하지 않는다.
- 공통 브랜치 이력을 다시 쓰지 않는다. 충돌 해결은 최신 develop을 작업 브랜치에 merge하고 다시 확인한다.

```sh
git add 변경한_파일
git commit -m "feat(ai): 영상 감지 이벤트 생성 (#12)"
git push -u origin feat/12-fire-events
```

파일·브랜치·메시지는 실제 작업으로 바꾼다. 예제의 자리표시자를 그대로 실행하지 않는다.

### 4.5 PR 컨벤션과 템플릿

- 작업 PR 대상은 `develop`이며 제목은 커밋과 같은 `<type>(<scope>): <변경 내용> (#번호)` 양식이다.
- PR 제목 type은 브랜치 type과 일치시킨다.
- 본문에 `Closes #번호`로 해당 이슈를 연결한다.
- 완료한 변경·검증 결과·남은 제한을 작성한다. 실행하지 않은 검사를 “통과”로 적지 않는다.
- 개발 중이면 Draft, 머지 준비가 끝나면 Ready로 전환한다.
- 같은 이슈의 후속 수정은 같은 브랜치에 push한다. CI가 최신 커밋에서 다시 통과해야 한다.

실제 템플릿: [PR 템플릿](../.github/pull_request_template.md)

```markdown
## 연결 이슈
Closes #이슈번호

## 변경 내용
무엇을 바꿨는지와 그 이유

## 확인 방법 및 결과
실행한 검사·기대 결과·실제 결과
미실행 항목이 있으면 이유

## 남은 작업·주의 사항
없으면 "없음"

## 머지 전 확인
- [ ] 이슈·브랜치·커밋·PR 번호가 일치한다.
- [ ] 대상 브랜치와 병합 방식이 맞다: 작업은 develop/Squash, 배포는 main/Merge commit.
- [ ] 필요한 검사를 실행하고 결과를 적었다.
- [ ] 비밀정보·가중치·원본 영상이 포함되지 않았다.
- [ ] 공통 계약 변경은 관련 문서·샘플에 함께 반영했다.
```

### 4.6 CI와 머지

필수 체크 이름은 **`ci`**로 통일한다.

| 검사 | 적용 시점 |
| --- | --- |
| 문서 링크·형식, 협업 검사 자체 시험 | 모든 변경 |
| 브랜치·PR 제목·이슈 연결·커밋 양식 | PR |
| Python 의존성·시험 | backend 또는 ai_worker 코드가 생긴 이후 |
| 프론트 lint·test·build | web/package.json이 생긴 이후 |

문서만 있는 현재 단계에서는 아직 없는 제품 코드의 시험을 통과했다고 표시하지 않는다. 백엔드·프론트 최초 구현 PR에는 잠금 파일과 해당 시험·스크립트를 함께 넣는다. 실제 모델 추론·3D·단말·서버 시연은 자동 CI만으로 대체하지 않는다.

머지 조건과 절차:

1. Draft가 아니고, 대상 브랜치와 충돌이 없어야 한다.
2. 최신 커밋에서 `ci`가 통과해야 한다. 작업 PR은 최신 develop을 반영한 뒤 다시 검사한다.
3. 작성자가 변경 파일·검증 결과·완료 조건을 확인한다.
4. 작업 PR은 **Squash and merge**로 develop에 합친다. 최종 커밋 제목은 이슈 번호가 포함된 PR 제목을 유지한다.
5. 연결 이슈가 닫혔는지 확인하고 작업 브랜치를 삭제한다.
6. 담당자는 최신 develop을 받아 다음 이슈를 시작한다.

두 브랜치의 승인 리뷰 수는 **0명**이다. CI 실패·충돌은 수정해야 하지만 리뷰를 기다릴 필요는 없다. GitHub의 필수 상태 검사와 PR 규칙으로 develop·main을 보호한다. [GitHub 보호 브랜치 안내](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

충돌은 해당 파일을 함께 수정한 담당자와 의도를 확인해 해결한다. 통합 내용을 무조건 버리거나 강제 push로 덮어쓰지 않는다. 충돌 해결용 merge commit은 일반 작업 커밋 양식 검사에서 제외한다. develop에는 Squash된 작업 커밋이 쌓이고 main에는 배포 Merge commit이 남는다.

### 4.7 배포 PR

- 배포 이슈를 만들고 `develop → main` PR을 연다. 제목은 `chore(release): <배포 내용> (#배포이슈번호)`다.
- 배포 PR에는 포함한 작업·시연 버전·확인 결과·남은 제한을 기록한다.
- 배포 PR의 여러 커밋은 각자의 원래 작업 이슈 번호를 유지한다. 배포 이슈 번호로 모두 바꾸지 않는다.
- CI 통과 후 **Create a merge commit**으로 반영한다. develop → main에는 Squash를 사용하지 않아 이후 배포에서도 공통 이력을 유지한다.
- main은 develop의 배포만 받으며 별도 기능 수정은 하지 않는다. 배포 PR은 한 번에 하나만 진행한다.
- develop은 최신 base 반영을 필수로 한다. main 배포 PR은 별도의 main 동기화 커밋을 요구하지 않고 해당 PR의 CI와 충돌 여부를 확인한다.
- 기본 브랜치가 develop이므로 작업 이슈는 기능 PR 머지 시 자동 종료를 확인한다. main 대상 배포 이슈는 머지·검증 후 수동 종료한다.
- develop·main은 삭제하지 않는다. 검증·배포할 commit을 기록하고 서버에 반영한다.

### 4.8 인계와 AI 활용

- 인계할 때 이슈·PR, 변경 계약, 실행·검증 방법, 남은 오류를 함께 전달한다.
- ID·필드·상태·버전을 바꾸면 공급자·수신자·시험 자료를 함께 수정한다.
- AI에게 담당 이슈, 관련 명세, 변경 범위와 완료 조건을 전달한다.
- 생성된 코드·3D·시험 결과는 담당자가 확인한다. AI가 작성했다는 이유로 CI·실제 동작 확인을 생략하지 않는다.
- GitHub 팀원 계정과 역할을 확인한 뒤 저장소 Write 권한을 부여한다. SSH 개인키·AWS 키는 이슈·PR·저장소에 넣지 않는다.

## 7. 개발 순서

1. 공통 계약·작은 그래프·독립 기대 결과를 준비한다.
2. 시험 이벤트 → 상태 → 경로 → 별도 단말을 먼저 연결한다.
3. 실제 AI 이벤트와 기본 3층 공간 데이터를 연결한다.
4. 연기 변화·가상 관측·화면·단말의 흐름을 연결한다.
5. 단절·만료·역순·초기화·안내 불가를 확인한다.
6. 지원 서버에 배포하고 원격 접속·재시작·복구를 검수한다.
7. 고정 조건으로 평가하고 제출본·증거·백업을 정리한다.

시험 입력·초기화·자료 검증·실행 로그 검증은 3D와 독립된 도구로 제공한다. 구체적인 API·자료형은 05번, 시험 순서는 07번 문서를 따른다.

## 11. 지원 서버 배포 계획

사용자 제공 `4조_서버안내.html` 기준으로 Ubuntu 24.04·4코어·16GB·30GB 서버와 S3가 지원된다. 실제 자원·권한·GPU 유무는 접속 후 확인한다.

| ID | 담당·기한 | 내용 | 완료 기준 |
| --- | --- | --- | --- |
| D01 | 2·일 | 제공 접속·자원·권한·저장소 확인 | 서버와 S3 사용 가능 여부 확인 |
| D02 | 2 주관, 1·3 지원·화 | 후보 버전·웹 빌드·AI·제어·시나리오 배포 | 서버에서 실제 통합, 프로세스 유지 |
| D03 | 5 검수, 2 수정·수 | 다른 PC 접속·재시작·단절·복구, 공개 방식 결정 | 배포 범위별 재현·장애 확인 |
| D04 | 5 주관·목 | 제출 후보·증거·자료 보존 | GitHub·PC 백업, 필요한 S3 사본·제출 확인 |

- 초기 접속은 SSH 터널을 기준으로 하고 내부 제어 API를 무인증 공개하지 않는다.
- 공개 URL이 필요해지면 관람과 조작 권한·HTTPS를 정하고 해당 검증을 추가한다.
- CI는 배포 전 검사다. 자동 운영 배포는 현재 구성하지 않으며 담당자가 검증한 main 버전을 배포한다.
- 서버에서 AI·제어·시나리오를 별도로 실행한다. 관제와 SSH 관리 창이 닫혀도 서비스는 유지한다.
- 재시작은 새 run_id로 시작하고 준비·관측·시작 확인을 다시 한다.
- S3는 자료·실행 증거 보관에 사용하며 실시간 제어가 업로드를 기다리지 않게 한다.
- Bedrock 언어모델은 핵심 감지·경로 판단에 넣지 않는다.
- 행사 종료 후 서버·저장소가 삭제되므로 GitHub와 PC에도 자료를 보존한다.

설치·서비스 등록·배포 명령은 구현한 프로그램에 맞춰 실행 설명서에서 관리한다.
