# A01/A04 후속 검증 — 중복 경보 분석과 지속 실행

2026-11-10, #114. 개발 후보의 남은 중복을 분석하고 confidence 0.15 한 개만 비교했다. 공개 기본 모델/설정, 경보 창, 매칭·정답은 변경하지 않았다. 평가용 영상·구간 정답은 사용하지 않았다. 최종 모델 추천과 팀/담당 5 인계는 [평가 동결 제안](evaluation-freeze-and-handoff.md)을 따른다.

## 중복 원인과 제한된 후보 비교

원본 해시를 확인한 뒤 이전 실행의 정확한 샘플 프레임을 추출해 Codex가 확인했다. 이는 담당 5의 독립 정답 검수가 아니다.

- 촛불의 11011/11512ms에는 일정한 불꽃이 보인다. 12012/12513ms에는 밝게 번지는 불꽃과 성냥의 위치 변화가 보이며 영상에 불빛/불꽃이 사라졌다고 판단할 근거는 없다. xiazh 0.25는 이 두 샘플에서 FIRE 박스를 출력하지 않았고, 13013ms 재검출 후 지속 조건 때문에 13514ms에 ALARM을 재개했다. **밝기·모양 변화와 검출 실패가 함께 관찰**되지만 모델 내부 원인을 확정하거나 GT가 틀렸다고 판정하지 않는다.
- Tai Po의 1500/2000/2500/3000/3500/4000/4500/5000ms에는 배경에 옅은 연기 기둥이 보인다. 0.25는 가운데 2500~4000ms 샘플에서 SMOKE 박스가 없어 사건이 나뉜다. 희미한 연기·배경 변화가 원인 후보이며 전송 실패로 설명되는 단절은 아니다.
- ALARM 메시지 사이의 단절은 평가상의 예측 사건을 나눈다. 제어기는 기존 위험 원인을 유지하므로 이를 경보의 자동 해제/복구나 경로의 반복 전환과 혼동하지 않는다.

모델/640/500ms/window 1500ms/min 2를 유지하고 confidence만 0.25→0.15인 **후보 한 개를 사전에 지정**했다. 같은 개발 7개 전체를 한 번씩 실제 worker→자체 API로 실행했다. [원본 재계산 JSON](../../deploy/resource-checks/2026-11-10-ai-readiness-candidate.json)에 입력·설정·소스·예측 해시, 모든 사건·전송 결과와 두 문제 영상의 검출 타임라인이 있다.

| 설정 | FIRE TP / FP / FN | SMOKE TP / FP / FN | 정상 FIRE / SMOKE FP | 판단 |
|---|---|---|---|---|
| xiazh 0.25, #105 기준 | 1 / 1 / 0 | 2 / 1 / 0 | 0 / 0 | 추천 후보 유지 |
| xiazh 0.15, 이번 비교 | 1 / 1 / 0 | 2 / 2 / 0 | 0 / 1 | 미채택 |

촛불·연기 중복은 남고 LED 촛불의 SMOKE 오탐 사건 1개(ALARM 메시지 3개)가 추가됐다. 137.320초 정상 표본에서 단순 시간당 환산한 SMOKE 오탐은 26.22건이며 실제 1시간 관측 수치가 아니다. FIRE 정밀도 50%·재현율 100%, SMOKE 정밀도 50%·재현율 100%는 작은 **개발** 표본의 결과다.

358/358 샘플·365개 수신, 건너뜀/관측 만료 0, 7개 EOF/payload/제어 로그 검증 및 자체 제어기 종료를 확인했다. 첫 준비 시 잘못된 설정 키 `confidence_threshold`를 써 사전 검증에서 거부됐으며 분석 0·제어기 시작 전 실패 로그도 보존했다. 올바른 기존 키 `confidence`로 수정 후 전체 실행했으며 성능 결과가 나쁘다는 이유로 제외하거나 반복 탐색하지 않았다.

재현은 [A01-4 명령](a01-alternative-models.md)의 xiazh 설정을 별도 복사해 `confidence`만 0.15로 바꾸고 새 출력 폴더를 사용한다. 이전 비교와 같은 원본/GT 해시·모든 샘플 인덱스를 대조했다. 기본 설정에 이 후보를 반영하지 않는다.

## 단일 작업자 지속 실행

지원 서버에서 xiazh 0.25로 정상 개발 CAVIAR browse 영상 75.840초를 24회 연결한 1,820.160초 입력을 실행했다. 반복은 코덱 재압축 없는 `ffmpeg -stream_loop 23 ... -c copy`이며 전체 45,504개 YUV420p 프레임 해시가 원본 목록의 24회 반복과 같은지, 시각이 0부터 40ms씩 증가하는지 확인했다. 새로운 독립 장면이나 정상 정확도 표본을 추가한 것으로 계산하지 않는다.

검증 도구 `tools.validate_ai_delivery`에 `--worker-timeout-seconds`를 추가했다. 기본 240초는 유지하고 양의 정수 1~3600초만 허용한다. 지속 실행에는 2100초를 명시한다. 잘못된 값은 입력 읽기·제어기 생성 전에 거부하며, timeout 발생은 FAILED와 제어기 종료로 기록한다. 테스트는 기본값/명시값 전달과 timeout 실패·종료까지 확인한다.

```sh
python -m tools.validate_ai_delivery --output runs/sustained-result --manifest runs/repeated-development-manifest.json --asset-id dev-caviar-repeat24 --config configs/ai.xiazh.development.json --worker-timeout-seconds 2100
```

manifest의 파생 path/SHA-256과 development 표시는 실제 생성 파일에 맞춰 작성한다. 소스는 develop `9d708d5`에 이번 검증 도구 수정만 더한 버전이며 기존 AI 환경을 재사용한다. 별도 폴더·임시 loopback 포트·nice 10으로 실행하고 공용 WFI/서비스/방화벽을 바꾸지 않는다. 프로세스 RSS/CPU 시간은 5초 간격으로 표본 수집한다. 순수 predict 벤치마크나 여러 카메라 동시 부하 시험이 아니다.

실행 중 담당3의 #74 / PR #115(`3c58e47`)를 작업 브랜치에 통합했다. 변경은 CCTV 관제·3D 등 web 경로이며 실제 서버에서 실행한 AI/제어/검증 Python 소스는 동일하다. 이번 서버 실행은 새 CCTV 화면의 브라우저 인수 검증이 아니다.

늦어진 샘플을 버리는 기존 정책대로 처리됐으며 과거 영상을 새 관측으로 위장하지 않았다. 지연 직후 처리가 재개되고 3초 유효기간은 유지됐지만, 짧은 파일 시험의 skip 0 결과가 30분에서도 보장되지는 않았다. OS 스케줄링·모델 런타임·CPU 크레딧 중 근본 원인을 이 로그만으로 확정할 수 없다. 샘플 누락 0이 채택 조건이라면 현재 결과로 최종 채택하면 안 된다. 반복 실행으로 실패를 지우거나 경보·지연 제한을 느슨하게 바꾸지 않았다.

준비 스크립트의 사용하지 않는 샘플 목록 보조 계산은 `t+500` 방식으로 3,501개를 만들었다. 실제 worker는 고정 500ms 격자의 다음 경계를 사용한다. 이 보조 값은 실행을 제어하지 않았으며, 최종 검증은 검증된 40ms 프레임 시각에 worker의 `(media_ms//500+1)*500` 규칙을 적용해 **3,641개**를 독립 계산하고 분석/폐기 인덱스 전체와 대조했다. 원래 보조 값과 정정 설명도 증거에 보존했다.

원본 증거 묶음은 `runs/a01-114-evidence.tgz`, SHA-256 `8e511590cb14986a63ffc2a28a19e31c0058793cab83aa6813f0f948c3ee5540`이다. Git에는 가중치·영상·전체 로그를 넣지 않고 입력/소스/출력 해시와 집계를 남겼다. 실행 소스 raw 해시는 전송한 archive/파일의 실제 바이트, LF 정규화 해시는 로컬 소스 비교용으로 분리한다.
