# saferoute AI 개발·평가 계획서

[요구사항 F01](03-requirements-spec.md#f01-실제-불꽃연기-영상-분석) · [이벤트 계약](05-data-interface-spec.md) · [통합 시험](07-integration-test-demo-scenarios.md)

이 문서는 **오픈소스 불꽃·연기 모델의 실제 영상 추론**과 **Amazon Bedrock의 관제 상황 설명**을 분리해 개발·평가하는 절차다. 이 역할 분담은 2026-11-08 확정했다. 구체적인 감지 가중치·런타임·성능과 Bedrock의 실제 상황 설명 품질·지연은 아래 절차로 검증한다. [D01](../deploy/README.md)에서는 제공 Haiku 프로파일의 최소 호출 접근만 확인했으며 A05 완료를 의미하지 않는다. 모의 센서 성공과 설명 생성 성공을 감지 정확도로 계산하지 않는다.

## 1. 목표와 역할

| 구분 | 책임 |
| --- | --- |
| 1번 | 오픈소스 감지 선정·실행·영상·이벤트·평가, A05 Bedrock 설명 작업자 |
| 5번 | 자료 출처·사용 조건, 개발/평가 분리, 독립 정답, 결과 대조 |
| 2번 | 공통 입력·설명 계약, 관측·경보·경로, Bedrock 권한 확인·배포 |
| 3번 | 실제 영상 근거·AI 출처·관측 상태와 버전에 맞는 상황 설명 표시 |

화요일에는 실제 추론 이벤트가 제어·단말에 연결되어야 한다. 수요일에는 고정 조건에서 독립 평가와 실패 분석을 수행한다. 화요일 기능 연결과 수요일 성능 평가는 다른 완료 항목이다.

## 2. 모델 선정 기준

개발 후보의 실제 CPU 실행·6개 개발 영상 출처는 [A01 기록](ai/a01-model-validation.md), 입력 크기 비교·사용 조건·서버 측정 인계는 [후속 기록](ai/a01-selection-and-server-check.md)에 있다. A01-1 #79는 검증 자료의 팀 인계이며 A01 #9의 최종 선정이나 독립 평가 완료를 뜻하지 않는다.

### 2.1 확인 항목

| 항목 | 확인 방법 | 탈락 또는 보류 조건 |
| --- | --- | --- |
| 불꽃·연기 지원 | 모델 설명과 실제 클래스 목록·추론 출력 대조 | 기본 객체 클래스만 있고 불꽃·연기 없음 |
| 실행 가능성 | 시연 장비에서 영상 1개 실제 처리 | 설치만 성공하고 추론 실패 |
| 가중치 신뢰성 | 공식 배포·학습 출처·파일 해시 기록 | 출처·사용 조건 확인 불가 |
| CPU 처리 | 입력 크기·간격별 처리 속도·메모리 측정 | 제어 시연에 필요한 관측이 계속 만료 |
| 라이선스 | 코드·가중치·데이터 각각의 조건 확인 | 제출·재배포 범위와 충돌 미해결 |
| 결과 형식 | 클래스·confidence·프레임 시각 제공 | 이벤트의 필수 근거를 생성하지 못함 |
| 재현 | 버전·환경·명령 기록 | 실행 조건을 재현하지 못함 |

가중치 파일 확장자가 `.pt`라는 이유로 임의의 런타임에서 열 수 있다고 가정하지 않는다. 불꽃·연기 클래스명을 실제 출력에서 확인하고 FIRE·SMOKE로 매핑한다. confidence는 모델 점수이며 실제 화재 확률이나 인증된 위험도라고 표시하지 않는다.

### 2.2 권장 진행 순서

1. 사용 조건과 불꽃·연기 지원이 확인되는 공개 학습 모델 후보를 먼저 찾는다.
2. 정상·불꽃·연기 개발 영상에 실행해 두 클래스를 실제로 확인한다.
3. 입력 크기·추론 주기·처리 장비를 조정하고 속도와 검출 실패를 함께 비교한다.
4. 두 클래스 통합 모델이 적합하지 않으면 별도 모델 조합의 자원·일정 부담을 검토한다.
5. 신규 학습은 자료·시간이 확보되는 경우에만 선택한다. 화요일 연결을 새 학습 완료에 의존시키지 않는다.

선정된 모델이 없다면 파일에는 `미선정`을 기록한다. 실행하지 않은 후보를 최종 모델로 표시하지 않는다. 이 문서는 특정 모델의 성능·라이선스를 보증하지 않는다.

## 3. 자료 확보와 분리

### 3.1 영상별 manifest

`data/manifests/assets.json`의 영상 항목에는 다음을 기록한다.

- asset_id, 파일명·해시, 원본 출처 URL, 사용·공개·재배포 조건.
- 원본 영상 ID·촬영 장면 ID, 개발용/평가용 구분.
- 길이·FPS·해상도·코덱·실제 읽기 성공 여부.
- 정상·불꽃·연기·혼합·방해 요인.
- 정답 주석 파일, 주석자·검토자, 제외 사유.
- 건물 구역 매핑은 시연용 수동 매핑임을 표시.

출처가 있는 영상이라도 재배포가 자동 허용되는 것은 아니다. 허용되지 않는 원본은 Git·공개 웹에 올리지 않고 재현 가능한 확보 방법을 제공한다.

### 3.2 개발/평가 분리

원본 영상·촬영 장소·장면 단위로 나눈다. 같은 영상의 인접 프레임이나 잘라낸 구간을 양쪽에 나눠 넣지 않는다. 개발 영상으로 임계값·지속 조건을 정하고 평가 영상은 조건 고정 후 실행한다.

자료가 적어 독립 평가를 충분히 구성하지 못하면 표본 수·한계를 그대로 기록한다. 특정 건물 CCTV와 다른 인터넷 영상으로 평가했다면 현장 일반화가 검증된 것으로 말하지 않는다.

### 3.3 포함할 장면

| 유형 | 목적 |
| --- | --- |
| 불꽃만 보임 | FIRE 검출 |
| 연기만 보임 | SMOKE 검출 |
| 불꽃·연기 함께 보임 | 다중 클래스 처리 |
| 정상 실내 | 기본 오탐 |
| 조명·햇빛·반사·붉은 물체 | 불꽃 유사 장면 |
| 수증기·안개·먼지·흐림 | 연기 유사 장면 |
| 작은 대상·가림·어두움 | 실패 조건 파악 |
| 영상 종료·손상·읽기 실패 | 유효성·장애 처리 |

모든 유형의 자료가 확보되었다고 가정하지 않는다. 확보 여부와 부족한 범주를 표시한다. 실제 위험한 화재를 새로 만들어 촬영하지 않는다.

## 4. 추론 파이프라인

```text
영상 열기
→ 프레임 읽기·영상 시각 확인
→ 입력 크기 변환
→ 실제 모델 추론
→ 실제 클래스 매핑
→ 임계값·지속 조건 적용
→ 관측 이벤트 생성
→ 제어 API 전송·응답 기록
```

### 4.1 영상 시간

- 시연은 원래 재생 속도를 기준으로 관측을 발생시킨다.
- 처리 속도가 부족하면 오래된 프레임을 무한히 쌓지 않고 지연·건너뛴 프레임을 기록한다.
- 영상 파일을 가능한 빨리 분석하는 오프라인 속도 측정과 실시간에 맞춘 시연 지연을 구분한다.
- media_time_ms는 영상 위치이며 observed_at은 해당 프레임을 획득한 실제 UTC다. 분석 완료 시각은 상세 로그에 별도로 남긴다. 오래 걸린 분석을 새 관측으로 보이게 하려고 observed_at을 바꾸지 않는다.
- 감지 지연을 측정하려면 원본 위험 시작 시각과 재생 시작 매핑을 함께 기록한다.

### 4.2 지속 감지

단일 프레임 경보와 시간 누적 경보의 차이를 개발 영상으로 확인한다. 단순한 기준안은 최근 창에서 일정 수 또는 일정 시간 이상의 클래스 검출이 유지되면 ALARM을 내보내는 방식이다.

창 길이·필요 검출 수·confidence 임계값은 설정으로 관리하고 평가 전에 고정한다. 시간 기준과 프레임 수 기준을 혼용하지 않는다. 추론 FPS를 변경하면 동일 프레임 수가 다른 시간을 뜻하므로 재검토한다.

실제 AI 관측 조건과 제어기의 경보 유지 조건은 다르다. AI가 새 프레임에서 검출하지 못했어도 제어기는 명시적 확인 해제 전 원인을 유지한다.

### 4.3 상태 이벤트

| 상황 | 이벤트·처리 |
| --- | --- |
| 정상 분석, 경보 조건 미충족 | OBSERVATION·VALID |
| 불꽃 지속 조건 충족 | ALARM·FIRE·confidence |
| 연기 지속 조건 충족 | ALARM·SMOKE·confidence |
| EOF | UNAVAILABLE·EOF |
| 읽기 실패 | UNAVAILABLE·DECODE_FAILED |
| 프로세스 생존 확인 | HEARTBEAT. 새 프레임 관측을 대신하지 않음 |
| API 실패 | 같은 ID·순번으로 제한 재시도, 실패·관측 지연 기록 |

“불꽃 없음”을 “건물 안전”으로 변환하지 않는다. 영상에 보이지 않는 구역과 센서 신호는 별도 판단 근거다.

## 5. 구현 파일과 실행

| 파일 | 역할 |
| --- | --- |
| ai_worker/inference.py | 선택 모델 로딩·추론, 프레임·클래스·점수 |
| ai_worker/events.py | 지속 조건·이벤트 생성·재전송 |
| ai_worker/__main__.py | CLI·설정·종료·로그 |
| configs/ai.example.json | 비밀정보 없는 공통 설정 구조 |
| requirements-ai.lock.txt | 검증한 AI 실행 환경 |
| data/manifests/assets.json | 영상·가중치·사용 조건 |
| data/expected/ai/ | 독립 정답 구간 |
| tools/evaluate_ai.py | 평가 집계. A04에서 1번 구현, 5번 대조 |

기술 기준은 [개발계획서 2절](02-development-plan.md#2-기술-구성)을 따른다. PyTorch 설치는 OS·CPU/GPU를 선택하는 [공식 안내](https://pytorch.org/get-started/locally/)를 기준으로 한다. D01에서 지원 서버는 GPU 가속기가 없는 t3.xlarge로 확인했으므로 CPU 실행을 검증한다. 실제 설치 절차는 선택한 모델·장비에 맞춰 기록한다.

```sh
.venv-ai/bin/python -m ai_worker --config configs/ai.local.json --video data/videos/DEMO_VIDEO.mp4 --controller http://127.0.0.1:8000
```

모듈은 개발 후 실행 가능하다. DEMO_VIDEO는 실제 파일로 교체하고 실행 파일 경로는 사용하는 가상환경에 맞춘다. 시험용 샘플·모의 감지를 자동 대체로 사용하지 않는다.

통합 실행의 AI 작업자는 시작 시 session에서 run_id를 읽고 `runs/<run_id>/ai-predictions.jsonl`에 프레임 시각·추론 완료 시각·클래스·점수·지속 조건·전송 event_id를 기록한다. 제어기와 별도 파일에 쓰며 이벤트 수신 로그를 덮어쓰지 않는다. run_id가 바뀌면 이전 영상 결과의 전송을 멈추고 운영자의 새 실행을 기다린다.

완료된 단일 영상 실행의 평가 도구는 다음 인터페이스로 실행한다.

```sh
.venv-ai/bin/python -m tools.evaluate_ai --predictions runs/AI_RUN/ai-predictions.jsonl --ground-truth data/expected/ai/evaluation.json --output runs/AI_RUN/ai-evaluation.json
```

AI_RUN은 실제 실행 디렉터리로 바꾼다. 평가 도구는 출처가 SIM인 결과를 AI 성능 분모에 포함하지 않는다. [A04-1 실행·정답 형식](ai/a04-event-evaluation.md)의 예제는 형식 시험용이다. 실제 독립 자료와 목표 고정, 전체 평가·5번 대조는 A04의 남은 작업이다.

## 6. 평가 방법

### 6.1 평가 단위

기본 평가는 **클래스별 위험 사건 구간**으로 한다. 5번은 영상에서 불꽃·연기가 보이는 시작·종료 구간을 표시하고 1번과 모호한 경계를 검토한다. 겹치는 불꽃·연기는 클래스별로 따로 주석한다.

AI 경보 출력은 같은 클래스의 시간적으로 이어진 검출을 하나의 예측 사건으로 묶는다. 초기 평가 규칙은 간격 1,000ms 이하를 같은 사건으로 묶고 경계 허용 오차는 0ms로 둔다. 예측을 시작 시각순으로 확인하여 같은 클래스의 정답 구간 안에서 시작하면 아직 대응되지 않은 해당 정답과 일대일 대응한다. 한 정답에 여러 예측 사건이 생기면 첫 대응만 TP이며 나머지는 FP다. 정답 구간은 클래스별로 겹치지 않게 정리한다. 이 규칙은 평가를 위한 기준안이며 필요 시 개발 자료로 수정하되 평가 실행 전에 고정한다.

- TP: 해당 클래스 정답 사건을 대응된 실제 AI 예측이 검출.
- FN: 해당 클래스 정답 사건에 대응되는 검출 없음.
- FP: 정답 사건과 대응되지 않는 예측 사건.
- Precision = TP / (TP + FP).
- Recall = TP / (TP + FN).

분모가 0이면 100%로 처리하지 않고 N/A와 분모를 기록한다. 클래스별 값과 사건 수를 같이 제시한다. 전체 프레임 정확도 하나로 정상 장면이 많은 자료의 성능을 과장하지 않는다.

박스 정답과 평가 도구가 준비되면 mAP를 추가할 수 있다. 사건 구간 주석만으로 mAP를 계산하지 않는다.

### 6.2 지연과 오탐

| 지표 | 계산·기록 |
| --- | --- |
| 검출 지연 | 정답 위험 시작부터 최초 유효 AI 경보까지. 영상 재생 매핑 기준 |
| 추론 처리시간 | 프레임 전처리·추론·후처리 구분 |
| 처리량 | 실제 처리 프레임 수 / 실제 소요 시간 |
| 정상 영상 오탐 | 정상 영상 총 길이와 FP 사건 수, 시간당 오탐 |
| 미검출 | FN 수·영상·클래스·장면 |
| 건너뛴 프레임 | 수·비율·정책 |
| API 전송 지연 | AI 전송과 서버 수신 근거. 다른 시계 혼용 금지 |

감지된 사건만의 평균 지연은 미검출을 숨길 수 있으므로 FN을 반드시 나란히 적는다. 표본 수가 작으면 p95·최댓값 해석의 한계를 기록한다.

### 6.3 목표 고정표

| 항목 | 평가 전 목표 | 실측 결과 |
| --- | --- | --- |
| FIRE 사건 정밀도·재현율 | A03에서 합의·기록 | 미측정 |
| SMOKE 사건 정밀도·재현율 | A03에서 합의·기록 | 미측정 |
| 정상 영상 시간당 오탐 | A03에서 합의·기록 | 미측정 |
| 감지 지연·처리량 | 시연 장비 개발 실험 후 고정 | 미측정 |
| 관측 만료·실패 처리 | 계약대로 상태 전환 | 미실행 |

목표가 미정인 상태에서 성능 합격 판정을 하지 않는다. 목표를 못 맞추면 결과와 실패 원인을 보고한다. 결과를 본 뒤 목표를 낮추고 최초 통과처럼 기록하지 않는다.

## 7. 실패 분석과 재평가

실패 표에는 영상 ID, 원본 시각, 정답, 예측, 설정, 원인 추정, 확인 근거, 후속 조치를 기록한다. “조명이 원인일 것”처럼 추정은 추정으로 표시하고 확인되지 않은 사실로 쓰지 않는다.

평가 영상으로 임계값을 바꾸면 해당 영상은 개발에 사용된 자료가 된다. 추가 독립 평가를 확보하거나 재사용 사실을 명시한다. 같은 장면의 프레임을 늘려 독립 표본 수처럼 보고하지 않는다.

## 9. Bedrock 상황 설명 개발·평가

- **범위:** 제어기가 확정한 활성 원인·차단·경로·안내 불가 사유를 관제 사용자에게 설명한다. 피난 방향·경보 해제·물리적 안전을 모델이 새로 결정하지 않는다.
- **모델:** 지원 안내문의 `global.anthropic.claude-haiku-4-5-20251001-v1:0`을 첫 후보로 사용한다. D01에서 서버 역할·리전·실제 접근·한도를 확인하고 A05에서 호출한다. 필요한 경우 허용된 Sonnet 4.6과 동일 입력으로 비교하되 감지 모델과는 별도 선정 기록을 남긴다.
- **연결:** `explanation_worker`가 `/api/state`를 읽고 Converse를 호출한다. 상태 조회·입력 사실 추출·응답 검사·별도 API·설명 로그를 구현하며, 제어 코드에서 모델 호출을 기다리지 않는다. 상세 구조는 04번 11절, 데이터는 05번 11절이 기준이다.
- **출력:** 지원 모델의 구조화 출력으로 summary·fact_refs를 받고 서버에서 검사한다. [AWS 구조화 출력](https://docs.aws.amazon.com/bedrock/latest/userguide/structured-output.html)은 형식을 제한하는 기능이며 사실 정확성 보장이 아니다. 첫 스키마 준비 지연은 실행 전에 측정하고, 예열 호출과 실제 사건 지연을 구분한다.
- **호출 기록:** 모델 ID·리전·프롬프트 버전·설정·근거 사실·run_id·안내 버전·요청/응답 시각·토큰·채택/폐기 사유를 남긴다. 초기 5초 timeout·5초 호출 간격·15초 근거 유효기간·512토큰은 측정 후 확정하며 입력 관측의 3초 유효기간을 늘리는 용도로 사용하지 않는다.
- **평가:** G01·G02·G04·G07·G09의 고정 사실로 정상·우회·경로 없음·관측 불가·복구 설명을 비교한다. 잘못된 위험/출구/방향, 안전 단정, 없는 근거, 지난 버전 채택, 지연·실패·사용량을 기록하고 5번이 문장별로 대조한다.
- **장애:** 권한 거부·429·timeout·형식 오류·오래된 응답·작업자 종료 중에도 기존 경로·명령·ACK가 유지되어야 한다. 실제 호출 성공과 장애 주입을 모두 V15에 남긴다. 단순 템플릿·모의 응답은 Bedrock 성공으로 계산하지 않는다.
- **인계:** A05 #41이 계약·작업자·조회 API를 제공하고 P02 #21이 관제에 현재 버전의 READY만 표시한다. 감지 성능 A04와 설명 품질 V15의 수치·실패를 별도로 제출한다.
